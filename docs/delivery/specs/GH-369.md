# Compromisso: descrição copiada do ticket como texto puro, sem tags HTML

Identidade: GH-369 (sem card Multica), Tier 1 (recomendado), follow-up da DMTE-558 (decisão D3, PR #374). Issue GitHub: dmrepositorio/aponta#369. Base: `origin/main` @ ac0a21f. Status da SPEC: decisões D1 a D3 tomadas pelo Alfredo; pronta para /plan.

## Objetivo
Ao vincular um ticket a um compromisso, o campo Descrição é preenchido com a descrição do ticket. Essa descrição é HTML do editor rico (`<p>…</p>`); hoje o modal copia o HTML cru, cortado em 160 caracteres, e o usuário vê tags literais, às vezes cortadas no meio (`<p>Erro na emis`). Passa a copiar texto puro derivado do HTML, inteiro, sem o corte de 160. Usuário: quem agenda compromisso a partir de um ticket. Sucesso: nenhuma tag nem entidade literal no campo; qualquer corte (teto de segurança) é feito sobre o texto, nunca sobre o HTML.

## Decisão de produto (D1, decidida)
O campo Descrição do compromisso é um `<textarea>` e vai para a API como string simples (`description: description || undefined`, `AppointmentModal.tsx:159`). Opções:
- A (recomendada): texto puro derivado do HTML. Muda só a cópia; o textarea, o payload e a exibição do compromisso ficam como estão. Tier 1, só front.
- B: conteúdo rico (trocar o textarea por `EzRichText` e renderizar com `RichContentView` no detalhe do compromisso). Muda a semântica do campo, o que já está gravado (texto puro legado) e a tela `CompromissoDetailModal`; pede sanitização e contrato de armazenamento, e sobe para Tier 2.

Decidido: A. É a mais simples e segura (nenhum HTML é gravado no compromisso, então não há superfície nova de XSS) e é a primeira opção da issue. A opção B, se um dia for desejada, vira outra entrega.

## Situação atual (código observado)

- Campo: `<textarea rows={3}>` (linhas 385-393), texto puro.
- `RichContentView.tsx` decide por `HTML_TAG_RE` (linha 3) se o conteúdo é HTML; senão trata como texto puro (`whitespace-pre-wrap`) ou markdown de imagem. Usa `DOMParser` (documento inerte) e já exporta `isBlankRichText` (27) e `isSafeMediaUrl` (38). Não há helper de HTML para texto.
- Teste atual: `AppointmentModal.test.tsx:188` liga ticket com descrição em texto puro (`Detalhe do chamado de teste`).

## Escopo
- Novo helper puro `richTextToPlainText(content: string): string` ao lado de `RichContentView` (`apps/web/src/components/tickets/`), reaproveitando o mesmo critério `HTML_TAG_RE` (exportá-lo ou compartilhá-lo) para decidir se é HTML.
- Em `handleSelectTicket`: derivar o texto com o helper (já com o teto de 2.000 aplicado sobre o texto) e remover o corte de 160.
- Testes (matriz abaixo).

## Contrato do helper
- Se o conteúdo não casa `HTML_TAG_RE`, devolve a entrada sem alteração (texto puro legado, inclusive `\n`, `<` e `&` soltos e markdown `![]()`).
- Se casa: `DOMParser` (`text/html`, inerte, nada executa) percorre a árvore. `script`, `style`, `iframe` e `object` são descartados; `br` vira `\n`; o fim de `p`, `div`, `h1-h3`, `blockquote` e `li` vira quebra de linha (`li` com prefixo `- `); `img` é descartada; as demais tags só contribuem com o texto dos filhos; entidades são decodificadas pelo parser (`&amp;` vira `&`, `&nbsp;` vira espaço). Colapsa mais de uma linha em branco seguida e faz `trim`.
- O retorno é texto: nunca contém tag vinda da entrada.
- Sem corte de 160 (D3). Teto de segurança de 2.000 pontos de código (`Array.from`, não parte par substituto) sobre o texto resultante; acima dele corta, `trim()` e acrescenta `…`. Texto de até 2.000 fica intacto.
- Mudança consciente de comportamento: o texto puro legado, que hoje é cortado em 160, passa a ser copiado inteiro até o teto.
- A descrição já digitada continua intocada: só preenche se `description.trim()` estiver vazio (comportamento atual).

Não se aplica: sem endpoint, query ou permissão novos. A descrição do ticket já chega ao front pela busca autorizada (`TicketSearchModal`); nada novo exposto. O valor continua indo pelo mesmo POST/PATCH de compromissos, como string.

## Critérios de aceite
- AC-01: Ao vincular ticket com descrição `<p>Erro no emissão da TOP 1100 </p>`, o campo Descrição fica `Erro no emissão da TOP 1100` (sem `<p>` nem `</p>`).
- AC-02: Descrição com vários parágrafos, `<br>`, `<strong>`, `<em>` e `<ul><li>` vira texto com quebras de linha (parágrafo e `br` viram `\n`, item de lista vira linha com `- `), sem nenhuma tag.
- AC-03 (teto): Descrição HTML com mais de 2.000 pontos de código de texto, com `<strong>` e entidade perto da posição 2.000, resulta em no máximo 2.000 pontos de código mais `…`, sem `<` nem fragmento de tag ou entidade. Descrição HTML longa abaixo do teto (ex.: 500 caracteres) entra inteira, sem `…`.
- AC-04 (entidades): `&amp;`, `&lt;` e `&nbsp;` aparecem decodificados (`&`, `<`, espaço); o corte nunca deixa meia entidade (`&am`), porque opera sobre texto já decodificado.
- AC-05 (legado texto puro): Descrição sem HTML (`Detalhe do chamado de teste`, ou `linha 1\nlinha 2`) é copiada integralmente, quebras incluídas, até o teto de 2.000; acima, corta com `…`. Mudança consciente: antes cortava em 160, então um texto puro de 200 caracteres agora entra inteiro.
- AC-06 (segurança): Descrição com `<p>Ok</p><script>alert(1)</script><img src="javascript:alert(1)" onerror="alert(1)">` copia só `Ok`: sem `alert(1)`, sem tag, nada executado.
- AC-07: Se o usuário já digitou descrição, selecionar ticket não a sobrescreve; o título continua sendo preenchido com o título do ticket.
- AC-08: O payload enviado ao salvar usa o texto puro do campo (`description: 'Erro no emissão da TOP 1100'`), nunca HTML.
- AC-09: Regressão: `AppointmentModal.test.tsx` e `CompromissoDetailModal.test.tsx` existentes, `RichContentView.test.tsx`, typecheck e build seguem verdes sem alterar teste existente.

## Riscos
- Descrição longa entra inteira no campo (até 2.000); o textarea tem `rows={3}` e o usuário edita. Compromissos novos podem ter descrição bem maior que antes.
- Fidelidade: listas aninhadas, tabelas e links perdem estrutura e URL no texto puro (o link vira só o texto). Aceitável para um campo editável.
- Texto puro legado com `<b>`, `<div>` etc. literais (código colado) será interpretado como HTML e perderá as tags; mesma ressalva já aceita na DMTE-558. Improvável.
- Descrição só com `table`, `s`, `mark` ou `code` não casa `HTML_TAG_RE` (D4 da DMTE-558) e é copiada crua como hoje. Mantido de propósito, por coerência com o renderizador.
- `DOMParser` no Vitest exige ambiente jsdom (já usado por `RichContentView.test.tsx`).
- Sem dados reais em fixtures: textos sintéticos.

## Decisões (Alfredo)
- D1 decidida: texto puro derivado do HTML (opção A), não conteúdo rico (B, Tier 2). Justificativa: o campo é um textarea editável e a API guarda string simples; nada de HTML entra no compromisso.
- D2 decidida: markdown legado de imagem `![alt](url)` fica literal no campo. Justificativa: é texto que o usuário pode editar, sem conversão extra.
- D3 decidida: sem o corte de 160; a descrição inteira em texto limpo, com teto de segurança de 2.000 pontos de código. Justificativa: o campo é um textarea editável e o corte de 160 existia para conter HTML cru, o que a conversão resolve. Muda conscientemente o comportamento do texto puro legado (antes cortava em 160).

## Tier
